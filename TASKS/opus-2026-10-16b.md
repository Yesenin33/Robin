## 1. A v4 pool that uses native ETH can never be quoted (blocks 1 870 tokens)

`app/services/swap.py: v4_pool_key()` accepts a pool only on an exact currency match:

```python
want = {token.lower(), quote.lower()}
...
return key if {row.currency0.lower(), row.currency1.lower()} == want else None
```

In v4 a native-ETH pool has `currency0 = 0x0000…0000`, but the caller passes `settings.swap_weth` for
the ETH leg. So the comparison fails and the quote answers *"We couldn't find a pool to quote this
trade"* even though the pool and its key are known and correct.

Measured now, with the keys fully backfilled:

- `pools` rows with native ETH as one currency: **2 114 of 4 732**
- tokens pointing at such a pool and therefore unquotable: **1 870**
- tokens whose pool pairs WETH/USDG (quotable today): **1 828**

Example: `0x05517f08e0bb2d7d8ab25f98e5c2828fdba6386c` (`STREAM`) — pool
`0xd65c6ccb0d556310de3ef96636da81485b6f3e572d92b2ba2a787e9c3ad26980`, fee 2500, spacing 25,
hooks `0x0`, currency0 `0x0`, currency1 the token. `POST /swap/quote` → *no pool*.

Required:

- The ETH leg matches `address(0)` **and** `swap_weth` (they are the same thing to the user); the key is
  built from **the pool's actual currencies**, never from the request's.
- The calldata for the native case settles/unwraps correctly (the router already has the ETH path —
  make sure `CMD_UNWRAP_WETH` / native settle is chosen from the pool's currency, not from the request).
- A regression test with a native-ETH v4 pool that asserts a quote comes back with a real `amount_out`
  and a `tx.to` equal to the configured router. Quote-only: never send a transaction.
- Keep saying "no pool" loudly when the pool really is not between the requested pair.
