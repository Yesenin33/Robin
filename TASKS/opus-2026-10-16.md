## 1. The portfolio hides most of what the user owns (highest impact)

Measured on `0x26a1a7c87f72fe37ca57ab92f24353ff12b1110a`: `alchemy_getTokenBalances` returns **47 non-zero
ERC-20 balances**; only **3** of those addresses exist in our own `tokens` table, and `PortfolioService._compute`
keeps only the known ones:

```python
pairs = [(by_addr[a], raw) for a, raw in held.items() if a in by_addr]
```

So 44 real holdings are invisible. The owner: *"there are many coins worth practically nothing, why can't I see them"*.

Required:

- Every non-zero balance the chain reports gets a row — indexed by us or not.
- For tokens we never indexed: `symbol` / `name` / `decimals` in **one batch** of `eth_calls` (never one
  request per token), and price + pool liquidity from DexScreener's batched tokens endpoint (up to 30
  addresses per request) behind a short Redis cache. Liquidity matters: it decides whether a value is real.
- A token with no market data still appears — symbol if known, value `—`/0. Never a made-up number, never a
  silent drop.
- Wrap those lookups so one odd token cannot fail the whole page.
- A portfolio load stays well under ~2 s warm and must not sweep one `balanceOf` per known token (2 900 of
  them) — that is what made `/portfolio` a 502 earlier today.

## 3. A pasted contract leaves the user staring at skeletons for ~70 s

Reproduced with the phone's exact request:

```
curl -s -w "%{http_code} %{time_total}" localhost:8000/safety/0x0107ad33b6e2b4b84bbb4487151fb39b8ae7acf2
-> HTTP 200 in 69.6 s      (a correct DANGER verdict, 69 seconds late; the API logs "slow_or_failed_request")
```

Cause: `SafetyService.get()` runs the full scan **inline inside the HTTP request** when nothing is cached
(`safety_service.py:131`). No queue, no 202, no progress — `Safety.tsx` shows `<Skeleton rows={3}/>` for the
whole duration. This is the path for **every** address the user pastes that we have not indexed.

Required: a request must never hold a socket for a scan. Return immediately (202 + a handle the client can
poll) or stream progress. The screen must show what is happening ("checking holders…", elapsed time) and
always offer a way out. A user-pasted token goes to the **priority** queue and must never queue behind bulk
work. Never show a verdict before it exists; UNKNOWN stays a possible, honest answer.

## 4. "Paste address" does not work on a phone, and the field has no submit

`Safety.tsx:65-69`: the empty-state CTA reads `navigator.clipboard.readText()`. The expression

```js
(await navigator.clipboard?.readText().catch(() => ''))?.trim() ?? ''
```

short-circuits to `undefined` when the Clipboard API is missing, then reports *"No token address in your
clipboard"* — a silent failure. On iOS the read needs focus/permission anyway. And `AddressBar`
(`Safety.tsx:74-82`) submits **only** on Enter, so a manually pasted address has no button to press.
Owner: *"the paste button doesn't work, I have to enter it by hand"*.

Required: an explicit visible submit ("Check") beside the input that works with a typed or pasted address; a
paste affordance that cannot fail silently (if the clipboard read is refused, say so and focus the input
rather than pretending the clipboard was empty); keep Enter working; keep the lowercase normalisation and
the `isAddress` guard.

## 6. Swap inside the app, confirmed in the wallet, not on another site

Today Buy/Sell deep-link to `app.uniswap.org` (`VITE_SWAP_URL`). The owner wants the confirmation in-app: we
build the transaction, the user's own wallet shows its confirm dialog immediately, no redirect.

Verified in Uniswap's own chain metadata for Robinhood Chain (4663): `supportedURVersions`
[UniversalRouter 2.0, 2.1.1], `supportsV4: true`, `backendSupported: true`; WETH
`0x0Bd7D308f8E1639FAb988df18A8011f41EAcAD73` matches ours; USDG
`0x5fc5360D0400a0Fd4f2af552ADD042D716F1d168`.

if a Uniswap Trading API key is configured (`SWAP_API_KEY`, empty by default) use it — it routes

Flow: amount → live quote → the token's **safety verdict shown in the same sheet** (this is the product:
nobody buys a DANGER token without seeing it) → one-time Permit2 approve when needed → send via
`eth_sendTransaction` on the connected provider → track the receipt → refresh the portfolio.

quietly, without re-prompting. Keep the external deep link as a fallback for wallets that cannot send.
Read the router and Permit2 addresses from configuration and **verify them against the chain** before the
first real swap. Tests for the quote/slippage math.

## 9. The v4 route never resolves — 96 % of tokens cannot be quoted

Measured on the deployed build: `POST /swap/quote` for a token whose liquidity is in a v4 pool returns
"We couldn't find a pool to quote this trade", while a v3-pool token quotes correctly (WETH→USDG: 10^16 wei
of WETH comes back as 24 602 346 USDG ≈ $24.6, and the fee-100 tier answers for other tokens too).

Cause: `swap.v4_pool_key()` resolves the PoolKey with

```python
rpc.call("eth_getLogs", [{"address": POOL_MANAGER, "topics": [INITIALIZE_TOPIC, pool_id],
                          "fromBlock": "0x0", "toBlock": "latest"}])
```

A whole-chain range is refused by every configured endpoint (Alchemy caps `eth_getLogs` at 10 blocks, the
official node answers 429). Measured: that call returns **0 logs in 0.3 s** — it fails fast and silently, so
`v4_pool_key` returns None, no v4 candidate is ever built, and `find_route` reports NoRoute.

Scale: of 3 020 tokens, **2 907 (96 %) hold a v4 pool id** in `pair_address` and only 111 hold a v3/v2 pool
address. So in-app swap currently works for ~4 % of the catalogue — and misses exactly the new tokens people
want to trade. `pool_init_block` is already stored for 2 804 tokens.

Required:

- Resolve the v4 PoolKey from the token's `pool_init_block` (a narrow window around it), not from block 0 —
  the PoolManager `Initialize` log is emitted in the block that creates the pool.
- Where `pool_init_block` is missing (216 rows), backfill it from the indexer or the pool-id Initialize log
  over a bounded recent window; never fall back to a whole-chain scan.
- Better still, persist fee / tick spacing / hooks at discovery time — `chain_index` already parses those
  `Initialize` logs — so the swap never needs a historical log read at all.
- Keep the honest failure: when no route is found, say so; do not quote a number we cannot fill.
- Test: a v4-only token must return a real quote, and the no-route path must still be covered.

Until this lands the swap stays disabled (`SWAP_ENABLED=false`) and Buy/Sell keep using the external
Uniswap deep link, which works for every token.

## 12. A user-requested check must finish in seconds, and must show progress

Owner: "it hangs on the check." Measured: `GET /safety/0x0bd7d308f8e1639fab988df18a8011f41eacad73` returned
202 three times in a row, the UI showed "Waiting for a free checker… 0s so far · most checks take under a
minute", and the scan finished ~1 m 45 s later (`safety_scanned … verdict CLEAN score 75`). So the request
path is correct now (202 + poll, no held socket) — it is the WORK that is too slow, and the screen says
nothing useful while it waits.

Why: the explorer reads of every scan (bulk and user) pass one global gate (`EXPLORER_RPM`, currently 20/min),
and 47 bulk scans were queued behind the user's check. Two concurrent scans each crawl through that gate.

Required:

- Reserve capacity for a user-requested check: priority scans get explorer slots ahead of bulk reads; keep
  bulk concurrency low enough that it cannot starve them.
- Cut the work per check: reuse holders/market data already stored for that token when it is fresh; do not
  re-read what we already know just because a user asked.
- The screen must narrate progress with real stages ("reading holders…", "checking liquidity…") and an
  honest estimate, and keep the way out ("Stop waiting"). A static "0s so far" for a minute reads as a hang.
- If the token already has a recent verdict, show it immediately and refresh in the background instead of
  showing an empty skeleton.
- Target: a user-triggered check paints a result well under 15 s on a warm system; if it cannot, say what is
  slow.

## 13. Every token shows its own image, like every wallet does

Owner: "why don't the coins have their images? Every coin must have its own image like in all wallets."
Answer: we never capture them — the `tokens` table has no image column, `intelligence/market.py` reads

(`components/ui.tsx:Avatar` — a coloured circle with the first letter) for everything. A wallet that shows
letters where every other wallet shows token art looks unfinished, whatever else the app does.

Required:

- Capture the token image at scan/discovery time (DexScreener `info.imageUrl`; Uniswap's token list
  `logoURI` as a secondary source), store it, and expose it in the API rows that already carry `symbol`.
- Render it in the portfolio, the safety screen, the copy feed and any token row, sized and shaped for the
  layout; fall back to the monogram when there is none, and never let a broken or blocked image break a row.
- Backfill the tokens we already know (2 900+ rows); the next scan of each can fill it in, a bulk pass is fine.
- Keep it cheap: a batched, cached source — no per-render fetch.
